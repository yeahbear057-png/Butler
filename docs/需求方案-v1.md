# 个人信息管家 · 需求方案 v1.2

> 融合 Mem（自动关联）、Reflect（每日笔记 + 双向链接）、Notion（问答 Agent + 集合）三种形态，在现有「个人信息管家」上做一次结构升级。
>
> 版本：**v1.2**
> 状态：**功能范围已全部确认，待排期实现**
> 适用版本：现有线上版（收件箱 / 待办 / 智能问答 / 阶段总结）
>
> v1.1 变更：确认纳入的全部功能；新增「版本管理」。
> v1.2 变更：版本管理明确**永久免费、不分级、不设额度**（第 5.8.0 节）；移除 20 版 / 90 天的保留门槛，改为与付费无关的容量保护（第 5.8.7 节）；界面新增「禁止出现」清单（第 5.8.5 节）。

---

## 1. 这版方案要解决什么问题

现在的应用是一个「收 → 整理 → 问」的单向管道：东西丢进收件箱，AI 分类完就沉底了。用久了会遇到四个具体问题：

| 问题 | 现在的表现 | 这版怎么解 |
|---|---|---|
| **找不到关联** | 想不起上个月记过一条类似的想法，只能靠搜索框碰运气 | 每条记录旁边常驻「管家动态」侧栏，自动列出相关记录、相关标签、可提取的行动 |
| **没有时间线** | 记录只有创建时间，看不到"我这周都在想什么" | 每日笔记 + 月历视图，按天回看 |
| **只有 AI 猜，没有自己指** | 关联全靠 AI，用户想手动把两条笔记连起来做不到 | 双轨制：AI 语义关联 + 手写 `[[标题]]` 手动链接，两条都保留 |
| **改坏了回不去** | 编辑是覆盖式的，改完旧内容就没了；AI 重新整理一次更是直接覆盖手写原文 | 每次保存前留快照，能看历史、能逐行对比、能一键恢复 |

一句话：**从"存档工具"变成"越用越密的网"，并且这张网可以随时倒带回上一针。**

## 2. 参考产品拆解

### 2.1 Mem：把自己的 AI 藏在一个侧栏里

Mem 最值得学的是**不打断**。主编辑区始终干净，右栏「Heads up」安静地摆着三块东西：

- **相关记录**（按时间分组，带来源笔记的小标签）
- **可提取的行动项**（"Finalize campaign launch" 这类，能一键变待办）
- **相关集合**（`# Acme Co · 321 notes`）

关键细节：侧栏不弹窗、不抢焦点、不写"AI 正在思考"。它就是一张常驻的关联清单，用户想看就看。

> 我们要抄：侧栏的**位置**和**安静程度**。
> 我们不抄：Mem 那种"后台持续扫描所有内容"的重型索引（当前架构撑不住，也不必要）。

### 2.2 Reflect：每日笔记 + 双向链接

Reflect 的骨架是「一天一页」。左侧日历点哪天就是哪天，页面里写当天的流水，`[[ ]]` 一写就自动成链，右侧显示当天有哪些笔记和会议。

两个能直接用的细节：
- **月历用圆点/高亮标记"这天有内容"**，一眼看出哪天空了
- **反向链接显示在页面底部**，格式是"哪些笔记提到了我"

> 我们要抄：一天一页 + 月历 + `[[ ]]` 语法 + 反链区块。
> 我们不抄：块级（bullet-level）嵌套编辑器和端到端加密（成本高，收益对这版不明显）。

### 2.3 Notion：问答 Agent 和集合

Notion 的 Q&A Agent 有两个设计值得学：
- 答案旁边直接给**来源条目**，点击跳到原文
- 同一个问题被问过，答案会**沉淀进"Answers"列表**，下次不用重问

集合（Collection）本质是"带属性的页面列表"，它解决的问题是：**同一个主题的内容散在很多地方，需要一个容器**。

> 我们要抄：来源卡片 + 答案沉淀 + 集合作为聚合容器。
> 我们不抄：自定义属性/视图/公式那套数据库引擎（对我们来说过重）。

### 2.4 功能取舍总表

| 功能 | 来源 | 纳入 | 说明 |
|---|---|---|---|
| 管家动态侧栏（相关记录/行动/集合） | Mem | ✅ P0 | 核心增量，成本最低收益最高 |
| 后台自动整理（保存即分类） | Mem | ✅ 已有 | 现有能力，保留 |
| 对话中"Show thoughts"（展示整理过程） | Mem | ✅ P1 | 复用现有流式输出，加一个折叠区 |
| 每日笔记 | Reflect | ✅ P0 | 新增视图 |
| 月历视图 | Reflect | ✅ P0 | 新增视图 |
| 手动 `[[双向链接]]` | Reflect | ✅ P0 | 用户明确要求 |
| AI 语义自动关联 | Reflect/Mem | ✅ P1 | 用户明确要求，与手动并存 |
| 反链区块（谁提到了我） | Reflect | ✅ P0 | 跟随手动链接一起做 |
| 问答来源卡片 | Notion | ✅ P1 | 现在只有 `[1]` 角标，升级为可点卡片 |
| 答案沉淀（Answers） | Notion | ✅ P2 | 问答结果可存为一条记录 |
| **版本管理（编辑历史 / 对比 / 回滚）** | 新增需求 | ✅ **P1** | 覆盖笔记与每日笔记，每次保存留快照 |
| 集合 Collections | Notion | ✅ P1 | 主题聚合容器 |
| 提纲/块级嵌套编辑器 | Reflect | ❌ | 与现在的纯文本+渲染器冲突大，收益低 |
| 端到端加密 | Reflect | ❌ | 与云端 AI 处理冲突 |
| 数据库属性/视图/公式 | Notion | ❌ | 过重 |
| 多人协作 / 分享链接 | 三者 | ❌ | 个人工具，先不做 |
| 移动端 App | - | ❌ | 先保证手机浏览器可用 |

## 3. 目标用户与典型场景

**人物**：一个人用，不做团队。记录密度大约每天 3–10 条，偶尔大段摘录。

**场景 A｜早上翻昨天**
打开默认落在「今天」，看到昨天写了一半的想法，底下自动列出「相关记录 3 条」，其中一条是两周前同一主题的。点进去，发现当时已经否掉过一个方案。

**场景 B｜写东西时需要素材**
写到"用户留存"，敲 `[[`，弹出笔记标题补全，选中「留存率拆解」——这条笔记立刻就出现在页面底部，之后从那条笔记也能反查到今天这篇。

**场景 C｜月底回看**
打开月历，看到这个月有 18 天有记录。点 12 号，那天记了 6 条，其中 2 条变成了待办、1 条变成了阶段总结里的结论。

**场景 D｜问一句**
"我关于产品方向的想法变过几次？" 系统检索出 5 条，按时间回答"变过两次：3 月想做工具，6 月转向做社区"，每条结论后面挂来源卡片，点开是原文。

## 4. 信息架构

左侧导航从 4 项扩到 7 项，右侧新增常驻侧栏。

```
│              │                                     │  (Heads up)      │
│ ● 今天    NEW │                                     │                  │
│ ○ 收件箱   12 │            主内容区                  │  相关记录   3 条  │
│ ○ 每日笔记 NEW│                                     │  可提取行动 2 条  │
│ ○ 日历    NEW │                                     │  相关集合   2 个  │
│ ○ 待办     5  │                                     │                  │
│ ○ 智能问答    │                                     │  ─────────────   │
│ ○ 阶段总结    │                                     │  今天你还没有     │
│              │                                     │  写日记 → 去写    │
│ ─────────    │                                     │                  │
│ 集合          │                                     │                  │
│  # 产品       │                                     │                  │
│  # 读书       │                                     │                  │
│              │                                     │                  │

└──────────────┴─────────────────────────────────────┴──────────────────┘
```

**导航变更**

| 项 | 状态 | 说明 |
|---|---|---|
| 今天 | 新增，默认首页 | 昨日未完成 + 今日记录 + 最近反链 |
| 收件箱 | 保留 | 增加 `[[ ]]`、附件、来源标记 |
| 每日笔记 | 新增 | 一天一页 |
| 日历 | 新增 | 月历，标记有内容的日子 |
| 待办 | 保留 | 增加"来自哪天/哪条笔记"溯源 |
| 智能问答 | 保留，升级 | 加来源卡片、可存为记录 |
| 阶段总结 | 保留 | 引用新的每日笔记 |
| 集合 | 新增 | 侧栏底部，主题聚合 |

> 「今天」和「每日笔记」的区别：**今天 = 仪表盘**（跨来源汇总，偏看），**每日笔记 = 一个页面**（纯手写，偏记）。很多产品会把两者合并，但合并后"今天"会变得不知道该写什么。
>
> **版本管理的入口不放导航**。它不是一个"要去的地方"，而是任何一条内容自带的属性——所以只出现在笔记详情页和每日笔记页头的「历史 · N」。放进导航会让人以为要主动去"管理版本"，实际上没人会这么做。

## 5. 各视图详细说明

### 5.1 今天（新增，默认首页）

**目的**：打开就能接上昨天的思路，不用先搜索。

**结构**（自上而下）
1. **日期头**：`10 月 19 日 · 周一`，右侧一个「写今日笔记」按钮
2. **昨日遗留**：昨天创建、今天还没动过的记录（最多 5 条），每条一个「继续」按钮跳到详情
3. **今日已记**：今天新增的记录流（复用现有卡片样式）
4. **等你决定**：昨天产生的待办里未完成的（最多 5 条），可勾选
5. **最近被提到**：最近 7 天里被 `[[ ]]` 链接过 2 次以上的笔记（说明这是当前正在发酵的主题）

**空状态**：早上第一次打开，只显示一个大输入框 + 一句"今天想记点什么？"，下面灰字提示"昨天你记了 3 条，其中 2 条还没跟进"。

**边界**：如果今天还没有任何记录，跳过第 3 块，不显示空标题。

---

### 5.2 收件箱（升级）

现有能力全部保留，新增三件事：

**a) 行内链接语法**
输入框支持 `[[笔记标题]]`。输入 `[[` 时弹出补全浮层：
- 有匹配 → 列出标题 + 类型图标 + 日期
- 无匹配 → 底部一行「新建笔记"XXX"」，点了创建一条空白笔记并直接建立链接（即 Reddit/Reflect 的"红链"逻辑）

**b) 来源标记**
每条记录带一个来源角标：`手记` / `剪藏` / `语音` / `问答`。剪藏和语音是 P2，但字段先留好，避免以后改表。

**c) 记录详情页（升级）**
点击卡片进入的不是弹窗，而是**右侧抽屉 + 左侧内容不动**（Mem 的做法）。抽屉内容：
- 原标题 / 标签 / 摘要 / 要点（现有）
- **正文（支持 markdown 渲染，`[[ ]]` 渲染成可点链接）**
- **手动链接区**：「这条指向 3 条笔记」「被 5 条笔记指向」
- **AI 关联区**（P1）：「可能相关 3 条」，每条带相似度标签（高度相关/有点关系），可「确认」或「不是」
- 顶部右侧：**「历史 · N」**（P1，见 5.8）
- 底部：编辑、删除、转为集合

---

### 5.3 每日笔记 + 日历（新增）

**每日笔记**
- 一天一页，主体是一个大文本框（markdown）
- 顶部显示：日期、星期、当天记录条数、**「历史 · N」按钮**（P1，见 5.8）
- 右侧（或底部）自动汇总：**当天创建的所有记录**（收件箱里的东西），只读卡片形式，点击跳转
- 底部：**当天待办**，可直接勾选
- 自动保存：停止输入 1.5 秒后落库；**每次落库前判断内容是否变化**，变了才写版本，避免打字过程中刷出几十个版本

**日历**
- 月视图，7 列，周一起始
- 每格显示：日期数字 + 内容密度点（0 条=空，1–2 条=1 点，3–5 条=2 点，6+=3 点）
- 有日记的日子，日期数字加粗或加深底色
- 点任意一天 → 右侧滑出该日详情（日记摘要 + 当天记录列表 + 当天完成待办）
- 顶部：「今天」按钮 + 左右切月
- 支持键盘方向键切换日期

**跨天处理**：以本地时区为准（`Asia/Shanghai`），跨零点后新记录归新的一天。不做"凌晨 2 点算前一天"这类特殊规则，太反直觉。

### 5.4 双轨关联（本方案的重点）

用户明确要求 **AI 自动关联** 和 **手动 `[[ ]]`** 都要。两者不是二选一，是同一条链接记录上的两种来源。

#### 轨道一：手动链接

**语法**：`[[标题]]`，全角 `【【】】` 也接受（中文输入法常见误触）。

**解析时机**：保存时（不是输入时）。输入时只做补全，不改内容。

**解析流程**
1. 正则抓出所有 `[[...]]`
2. 按标题精确匹配 `notes.title`
3. 命中 → 建 `links` 记录，`kind='manual'`
4. 未命中 → 提示"有 2 个链接还没有对应笔记"，可选择：立即创建空白笔记 / 忽略
5. 标题改名时，反查所有正文里含旧标题的链接，批量改写成新标题（避免死链）

**反链展示**：任何笔记详情底部「被 X 条笔记提到」，列出标题 + 引用该链接的那句话（上下文 30 字）。

#### 轨道二：AI 语义关联

**不新增模型调用。** 复用现有的 `tokenize` + `scoreNote` 打分函数，从「搜索」场景挪到「关联」场景。

**打分公式**（在现有基础上扩展）

| 维度 | 权重 | 说明 |
|---|---|---|
| 标题命中 | 6 | 现有 |
| 标签重合 | 5 | 现有，但改为「重合标签数 × 5」而非逐词 |
| 摘要命中 | 3 | 现有 |
| 要点命中 | 2 | 现有 |
| 正文命中 | 1 | 现有 |
| **同类型加成** | +2 | 新增（两条都是 `question` 说明是同一批疑问） |
| **时间邻近加成** | +3 | 新增：7 天内 +3，30 天内 +1 |
| **手动已链接** | 剔除 | 已经在手动轨道里的不再重复推荐 |

**阈值**：得分 ≥ 8 才算"相关"。得分 ≥ 20 标「高度相关」，8–19 标「有点关系」。

**展示位置**：只出现在记录详情的 AI 关联区，**不进侧栏**。侧栏只放已确认的关联，避免噪音。

**冷启动**：笔记少于 20 条时不做 AI 关联，直接显示"记录还少，多记几条之后这里会出现相关推荐"。

**用户反馈闭环**：每条推荐右侧有「没用」按钮，点了记进本地黑名单（`localStorage`），同一条不再推给同一篇。

### 5.5 管家动态侧栏（Heads up）

**常驻位置**：主内容区右侧，宽 300px。窗口 < 1280px 时自动收起为右侧一条竖线，点开浮层。

**四个区块**（自上而下，每块最多 5 条 + "查看全部"）

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 相关记录 | 与当前查看的笔记相关（手动链接 + 已确认的 AI 关联） | `links` 表 |
| 可提取行动 | 当前笔记正文里像行动的句子 + 已有待办 | 规则匹配 + 现有 `SYSTEM_TODO` |
| 相关集合 | 这条笔记在哪些集合里，以及同集合的其他笔记 | `collection_items` |
| 今日提示 | 今天还没写日记 / 待办超期 / 某主题已连续 3 天出现 | 本地规则，不调模型 |

**性能约束（重要）**
- 侧栏数据全部本地计算，**不触发任何网络请求**
- 「相关记录」直接从 `state.notes` 内存数组算，不算数据库
- 切换笔记时 200ms 内出结果，否则先显示骨架屏

**为什么要强调这个**：Mem 的侧栏是后台索引算出来的，我们用前端内存算，规模上限是已加载的 300 条笔记。超过这个量级要改成分页 + 服务端查询，见第 10 节。

### 5.6 智能问答（升级）

保留现有能力（流式输出、`[n]` 引用标注）。新增：

**a) 来源卡片**
答案下方不再是纯文字角标，而是横排卡片：`[1] 留存率拆解 · 3月12日 · 资料`，点击在右侧抽屉打开原文并高亮匹配段落。

**b) Show thoughts（P1）**
答案上方一个可折叠的「管家怎么找的」，展开显示：
- 检索了哪些关键词
- 命中多少条、最终用了哪 5 条
- 一句话方法说明

实现上只是把已有检索过程结构化输出，不需要额外模型调用。

**c) 存为记录（P2）**
每条答案右侧一个「存下来」按钮，把问答对存成一条 `kind='material'` 的记录，来源标记 `问答`，自动带上原问题做标题。

**d) 答案沉淀（P2）**
同一问题被问过 3 次以上，在问答页顶部出现「常问的问题」列表，点了直接给上次答案（带"这是 9 月 12 日的回答，要重新基于最新记录回答吗？"）。

### 5.7 集合（Collections）

**定义**：一个有名字、有图标、能装笔记的容器。不做属性、不做视图，就是"文件夹 + 自动收录规则"。

**手动收集**：详情页「加入集合」→ 选择或新建。

**自动收集规则**（一条集合最多 3 条规则，AND 关系）
- 标签包含 `X`
- 标题/正文包含 `Y`
- 创建时间在某区间

新建集合时可选「按规则自动收录」，开启后新笔记保存时自动匹配。规则命中不弹窗，只在笔记详情里显示「已自动加入 #产品」。

**集合首页**：卡片网格，每张显示图标、名称、条数、最近更新。现有「常用标签」区域保留，标签点击 → 生成临时视图（不是集合，不持久化）。

### 5.8 版本管理（新增）

**要解决的痛点是具体的**：现在的编辑是覆盖式的。你改了一句话，原来那句就没了；更危险的是点「记录并整理」让 AI 重跑一次，它会用新的摘要和要点覆盖掉旧字段。**手写的东西被机器覆盖一次，人是会生气的。**

#### 5.8.0 三条不可妥协的原则

这一节先于所有交互细节，任何实现如果违反这三条，就是做错了。

**① 永久免费，不向用户收任何钱**

版本管理不产生任何费用。没有付费解锁、没有按次计费、没有订阅、没有"高级功能"。你记录、编辑、回看历史、对比、恢复——全部免费，且不需要任何账号等级。

**② 不做会员分级，不做企业版**

不存在「免费版 / 专业版 / 企业版」这种分层。全部用户、全部功能一致。文档里不出现价格、套餐、席位、席位数量、并发数、"升级"入口。

**③ 不按用量设限**

不限制版本条数、不限笔记数、不限对比次数、不限恢复次数。**没有"你已用完本月免费额度"这类提示**，因为不存在额度。

> 这三条不是营销话术，是排期和验收的一部分：任何界面文案里出现价格/套餐/升级/额度，验收不通过。
>
> 唯一存在的技术性约束见 5.8.7，那是为**防止存储无限膨胀拖垮性能**的保护，与付费无关，且对所有用户一视同仁。

#### 5.8.1 覆盖范围

| 对象 | 是否留版本 | 说明 |
|---|---|---|
| 笔记（`notes`） | ✅ | 正文、标题、标签、摘要、要点全量快照 |
| 每日笔记（`daily_notes`） | ✅ | 一天一页，改稿最多，最需要 |
| 待办（`todos`） | ✅ 仅记录状态变更 | 只留「谁在什么时候把它勾了/取消了」，不做全文快照（一句话的东西没必要） |
| 集合 | ❌ | 只是容器，改动无创作价值 |

#### 5.8.2 快照式存储，不是 diff 式

**决定：存全量快照，不存行级差异。**

理由：一条 500 字的笔记快照约 1.5 KB，一条笔记留 200 版也就 300 KB；而实现 diff 存储要维护链式重建逻辑，一处算错整条历史就废了。**用这点空间换掉一整类 bug，划算。**

> 规模估算：假设 1000 条笔记，平均每条 8 个版本，约 12 MB。就算每条都写到 200 版上限，也只有约 300 MB，对 PostgreSQL 来说仍在可接受范围。

#### 5.8.3 写入时机（关键设计）

**保存时，先写快照，再更新主体。**

```
用户点保存
  ├─ 1. 比对：内容/标题/标签/摘要/要点 全部没变 → 直接返回，不写版本
  ├─ 2. 快照：把【改动前】的完整数据写进 revisions，version = 当前最大版本 + 1
  ├─ 3. 更新：写 notes 表
  └─ 4. 清理：只有当体积真的撞到天花板时才删老版本（见 5.8.7，正常使用不会触发）
```

这样设计的好处：**当前内容永远只在 `notes` 表里读**，历史版本只用于回看和恢复。不需要"最新版本可能在 revisions 也可能在 notes"这种双读逻辑，读路径保持单线。

#### 5.8.4 版本来源标记（`op` 字段）

每条版本带一个来源，界面上显示成小标签：

| op | 含义 | 触发场景 |
|---|---|---|
| `edit` | 手动编辑 | 用户在详情页改字 |
| `ai_organize` | AI 重新整理 | 点了「重新整理」，摘要/标签/要点被模型重写 |
| `link_sync` | 链接改名同步 | 其他笔记改名后，正文里的 `[[旧名]]` 被自动改写 |
| `rollback` | 回滚产生 | 恢复旧版后，被覆盖的那一版也会留下快照 |

**为什么 `rollback` 也要留版本**：回滚本身是一次覆盖。如果回滚不产生快照，用户连"我刚才手滑点错了"都救不回来。

#### 5.8.5 界面

**入口**：笔记详情页顶部，标题右侧一个「历史」按钮，带小角标显示版本数（`历史 · 7`）。每日笔记同样在页头放一个。

**版本抽屉**（从右侧滑出，不跳页）：

```
┌──────────────────────────────────┐
│ 历史版本 · 7              关闭 ×  │
├──────────────────────────────────┤
│ ● 现在          10-19 14:32      │
│   1,240 字                        │
│                                  │
│ ○ 14:02  edit       1,180 字 +60 │
│ ○ 13:40  ai_organize 1,120 字     │
│ ○ 10-18 22:15 edit  980 字  -140 │
│ ○ 10-18 09:02 edit  1,120 字      │
│ ...（全部版本，滚动查看）          │
└──────────────────────────────────┘
```

- 每条显示：时间（当天只显示时分）、来源标签、字数、相对当前的字数增减
- 点某一条 → 抽屉切换为**只读快照视图**，底部两个按钮：「与当前对比」「恢复这一版」
- 当前版本不可恢复，只能对比
- **列表不设「查看更多」「解锁更早版本」这类闸门**，有多少版本就列多少，滚动即可

**界面上不能出现的东西**（验收项）

| 禁止出现 | 原因 |
|---|---|
| 价格、「¥」、套餐名 | 版本管理不收费 |
| 「升级 / Pro / 高级版 / 企业版」按钮或角标 | 不分级 |
| 「剩余额度」「本月还可恢复 N 次」 | 不设额度 |
| 「版本数已达上限，去扩容」 | 不存在付费扩容 |
| 「免费用户仅保留 7 天」这类限制文案 | 所有用户一致 |

> 抽屉底部只放一句静态说明：`所有版本永久保留，可随时对比与恢复。` 不加任何按钮、不加任何链接。

**对比视图**：同一页面左右分栏（窄屏改为上下），行级 diff：
- 新增行：绿色底 `+`
- 删除行：红色底 `−`
- 未变行：常规灰
- 顶部一句摘要：`新增 3 行，删除 8 行，标签从 2 个变为 4 个`

**恢复确认**：点「恢复这一版」弹二次确认，说清后果——`当前内容会先存成一个新版本，然后被 10-18 22:15 的内容替换。可以再改回来。` 这句话必须写，它把"危险操作"降级成"可逆操作"。

#### 5.8.6 diff 算法

纯前端，行级 LCS（最长公共子序列），**不调模型**。

- 先按 `\n` 切行，行数 > 2000 时降级为"只标出不同的块，不逐行高亮"（避免浏览器卡住）
- 中文没有空格分词，行级对比足够；不做词级 diff（收益低、实现复杂）

#### 5.8.7 容量保护（与付费无关）

**先说结论：正常使用下，什么都不会被删。** 下面这些阈值是防呆用的天花板，不是套餐额度。

| 条件 | 处理 |
|---|---|
| 每个对象最近 **200 个**版本 | **一律保留**，不压缩、不折叠、不转成 diff |
| 200 个之外、且在 **2 年**内 | 保留 |
| 200 个之外、且超过 2 年 | 删除最老的几条 |
| 历史总体积超过 **2 GB** | 才启动一次清理，从最老的版本开始删 |
| 内容完全无变化 | 不产生版本（这是正常行为，不算删除） |
| 单条版本正文超过 50 KB | 照存，对比视图分段显示 |

按实际体型估算：1000 条笔记、每条 200 版、每版 1.5 KB ≈ 300 MB。**要碰到 2 GB，得写到几百万字**，正常个人使用不可能达到。

三条附加规则：

1. **清理绝不因为"额度用完了"触发**，只因为"体积真的太大了"。两者在代码里是两套判断，不共用阈值。
2. **清理前先提示**，不是静默删除：`有 3 个超过 2 年的旧版本将被清理，点此保留`。用户点「保留」就不删。
3. **清理只在保存时顺带做**，不依赖定时任务——定时任务要用云函数，会产生平台侧调用计费（这是云资源成本，不是向用户收的费）。

> 为什么还要留这个天花板：如果没有上限，一个每天改稿两百次的重度用户，几年后单是版本表就会到几十 GB，查询和备份都会变慢。**留一个几乎碰不到的上限，比赌"不会有人写到那个量级"更稳妥**——而且它对所有用户完全一样，不存在谁付费谁多。

#### 5.8.8 边界与异常

- **首次创建不留空版本**：新建笔记时 `version` 从 1 开始，但只在**第一次被修改时**才写快照（快照内容就是创建时的原文）。避免每篇笔记都多一条无意义的空版本。
- **多人/多设备同时改**：不做冲突合并。后保存的覆盖先保存的，但先保存的内容已经在 `revisions` 里了，能找回来。这是"有损失但可恢复"，比做 OT/CRDT 现实得多。
- **删除笔记**：`revisions` 一并级联删除（`on delete cascade`）。**不做"回收站"**，但删除前如果笔记有历史，提示一句`这条有 7 个历史版本，删除后一起消失`。
- **AI 整理失败**：不写版本（因为没有实际改动）。

## 6. 数据模型变更

现有三张表 `notes` / `todos` / `summaries` 全部保留。新增五张 + 两张扩字段。

### 6.1 新增表

```sql
-- 每日笔记：一人一天一条
create table daily_notes (
  id          uuid primary key default gen_random_uuid(),
  date        date not null,
  content     text not null default '',
  mood        text,                      -- 预留，暂不用
  owner_id    text not null default auth.uid(),
  created_at  timestamptz default now(),
  updated_at  timestamptz default now(),
  unique (owner_id, date)
);

-- 关联：手动 + AI 共用一张表
create table links (
  id          uuid primary key default gen_random_uuid(),
  from_id     uuid not null,             -- 源笔记
  to_id       uuid not null,             -- 目标笔记
  kind        text not null default 'manual',  -- manual | ai
  score       int  not null default 0,   -- AI 关联得分，手动为 0
  status      text not null default 'active',  -- active | dismissed
  context     text,                      -- 引用处上下文，反链展示用
  owner_id    text not null default auth.uid(),
  created_at  timestamptz default now(),
  unique (owner_id, from_id, to_id)
);

-- 集合
create table collections (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  icon        text default '#',
  color       text default 'default',
  rules       jsonb default '[]'::jsonb, -- 自动收录规则
  owner_id    text not null default auth.uid(),
  created_at  timestamptz default now()
);

-- 集合条目
create table collection_items (
  id             uuid primary key default gen_random_uuid(),
  collection_id  uuid not null references collections(id) on delete cascade,
  note_id        uuid not null references notes(id) on delete cascade,
  auto_added     boolean default false,
  owner_id       text not null default auth.uid(),
  created_at     timestamptz default now(),
  unique (collection_id, note_id)
);

-- 版本管理：全量快照，覆盖笔记与每日笔记
create table revisions (
  id           uuid primary key default gen_random_uuid(),
  target_type  text not null,             -- note | daily | todo
  target_id    uuid not null,
  version      int  not null,             -- 同一目标内递增，从 1 开始
  op           text not null default 'edit',  -- edit | ai_organize | link_sync | rollback
  title        text,
  content      text not null default '',
  summary      text,
  tags         jsonb default '[]'::jsonb,
  key_points   jsonb default '[]'::jsonb,
  word_count   int  default 0,
  rollback_from int,                      -- 若本次是回滚，记录恢复到哪一版
  owner_id     text not null default auth.uid(),
  created_at   timestamptz default now(),
  unique (owner_id, target_type, target_id, version)
);

create index revisions_target_idx on revisions (owner_id, target_type, target_id, version desc);
```

> `revisions` 的 `target_id` 不设外键，因为它同时指向 `notes` 和 `daily_notes` 两张表（多态）。级联删除在应用层做：删除笔记时同步 `delete from revisions where target_type='note' and target_id=...`。
> 之所以不用 `references notes(id) on delete cascade`：一旦将来加第三种对象，外键就锁死了。

**RLS**：五张表统一启用，策略与现有表一致——

```sql
alter table <t> enable row level security;
create policy "<t>_select" on <t> for select to authenticated, anon using (owner_id = auth.uid());
create policy "<t>_insert" on <t> for insert to authenticated, anon with check (owner_id = auth.uid());
create policy "<t>_update" on <t> for update to authenticated, anon using (owner_id = auth.uid()) with check (owner_id = auth.uid());
create policy "<t>_delete" on <t> for delete to authenticated, anon using (owner_id = auth.uid());
```

### 6.2 现有表扩字段

```sql
alter table notes add column pinned      boolean default false;   -- 置顶
alter table notes add column archived    boolean default false;   -- 归档（不删但不出现在列表）
alter table notes add column source      text default 'manual';   -- manual|clip|voice|qa
alter table notes add column daily_date  date;                    -- 归属日（用于日历聚合）
alter table notes add column ref_count   int default 0;           -- 被链接次数，冗余字段加速侧栏
alter table notes add column rev_count   int default 0;           -- 历史版本数，角标显示用
alter table notes add column rev_at      timestamptz;             -- 最后一次改动的快照时间

alter table todos add column remind_at   timestamptz;             -- 提醒时间（P2 用）
alter table todos add column from_date   date;                    -- 从哪天的笔记里拆出来的
```

`ref_count` 是冗余：每次 links 写操作后同步更新，避免侧栏每次都 count。数据量小时可不加，先留着。
`rev_count` 同理：详情页「历史 · 7」那个角标不该为了显示一个数字去 `count(*)`。

### 6.3 数据迁移

现有 `notes` 全部 `source='manual'`、`daily_date = created_at::date`、`rev_count = 0`。一次性 SQL，无停机。

**版本表不回填历史**：老记录上线前没留过快照，硬造一条"创建时的版本"没有意义（用户也分辨不出真假）。所以老记录的历史从第一次编辑开始算，界面上显示`从 10 月 19 日起开始记录版本`。

## 7. AI 能力清单与成本

| 场景 | 触发时机 | 模型调用 | 降级方案 |
|---|---|---|---|
| 分类整理 | 保存记录时 | 1 次（现有） | 失败则存原文，标记待整理 |
| 待办整理 | 点「让 AI 帮我整理」 | 1 次（现有） | 保留现有，失败提示重试 |
| 问答 | 每次提问 | 1 次（现有） | 现有错误处理 |
| 阶段总结 | 点生成 | 1 次（现有） | 现有 |
| **手动链接解析** | 保存记录时 | **0 次** | 纯正则，无失败可能 |
| **AI 语义关联** | 打开笔记详情时（按需） | **0 次** | 本地打分，无网络 |
| **侧栏行动提取** | 打开笔记详情时 | **0 次** | 规则匹配（"要/需要/记得/别忘"等句式） |
| 集合自动收录 | 保存记录时 | **0 次** | 本地规则匹配 |
| 问答 Show thoughts | 提问时 | 0 次（附加字段） | - |
| **写版本快照** | 每次保存且内容有变 | **0 次** | 纯数据库写入 |
| **版本 diff 对比** | 点「与当前对比」 | **0 次** | 前端行级 LCS |
| 版本差异的 AI 一句话概括 | 点「说说改了什么」 | 1 次（可选，P2） | 失败则只显示行级统计 |

**结论：这版方案几乎不增加模型调用成本。** 所有新增的智能能力都建立在已有的本地分词打分和规则匹配上，只有用户主动点按钮时才调模型。这是刻意设计的——云端模型调用受平台配额约束，不该被后台关联白白消耗。（配额是平台侧的云资源，与「向用户收费」是两件事，本产品不向用户收任何费用。）

## 8. 非功能需求

**性能**
- 首屏（已登录、有缓存）：1.5s 内可用
- 切换视图：无加载态，直接渲染（数据已在内存）
- 侧栏计算：200ms 内，超时显示骨架
- 保存记录：输入不清空、不跳转，后台完成后卡片淡入
- **版本列表：按需拉取，只查 `id/created_at/op/word_count` 四个字段**，不拉 `content`
- **单条快照：点开哪一条才拉哪一条正文**，避免一次把 20 个版本正文全下载（那是 20 倍流量）
- **diff 渲染：>2000 行自动降级**为块级差异，防浏览器卡死

**存储与增长**
- 版本快照约占总体积的 60%–70%，是这版最大的一块存储增量
- 1000 条笔记 × 平均 8 版 × 1.5 KB ≈ 12 MB，可接受
- 容量保护（200 版 / 2 年 / 2 GB 天花板）只在保存时顺带检查，不依赖定时任务；正常使用永远不触发删除
- **不做版本导出**：导出会把快照体积放大到用户磁盘上，价值不大

**容量上限（当前架构）**
- 单次加载 300 条笔记 / 500 条待办，这是现有硬上限
- 超出后需要：分页加载（滚动到底部加载更多）+ 服务端搜索
- **本期不做分页**，但要在记录超过 250 条时提示"记录较多，建议归档旧内容"

**错误处理**
- 所有写操作失败必须保留用户输入，不能因为网络问题丢内容
- 本地先写、再同步（乐观更新），失败标记「未同步」并自动重试 3 次

**隐私**
- 所有表走 RLS，用户只能看到自己的数据
- 不做跨用户推荐、不做全局搜索
- 剪藏/语音功能（P2）上线前要明确告知"内容会上传到云端做整理"

**兼容**
- 移动端（375px 起）可用：侧栏默认收起、日历改为周视图、导航收进底部 Tab
- 不做独立 App

## 9. 版本规划

### P0 · 骨架（对应"每日笔记 + 日历 + 手动链接 + 侧栏"）

| 项 | 验收标准 |
|---|---|
| 每日笔记视图 | 一天一页，跨天自动新建，切换日期保留内容 |
| 日历视图 | 月历显示内容密度，点日期出详情，方向键可切 |
| 手动 `[[ ]]` 链接 | 输入补全、保存后成链、反链区块正确、未命中可新建 |
| 管家动态侧栏 | 四个区块，相关记录/行动/集合，全部本地计算无请求 |
| 收件箱 `[[ ]]` 支持 | 记录正文里的链接可点击跳转 |
| 数据迁移 | 现有记录全部带上 `daily_date`，旧数据在日历上正确显示 |

**不在 P0**：AI 关联、集合、Show thoughts、来源卡片、剪藏、语音、提醒。

### P1 · 连通（对应"AI 关联 + 集合 + 来源卡片 + 版本管理"）

| 项 | 验收标准 |
|---|---|
| AI 语义关联 | 详情页出现「可能相关」，带相似度标签，可否定 |
| 集合 | 创建/重命名/删除，手动加入，规则自动收录 |
| 问答来源卡片 | 答案下方可点卡片，跳转高亮 |
| Show thoughts | 折叠区显示检索过程 |
| 链接改名同步 | 笔记改名后正文里的 `[[旧名]]` 自动改写 |
| **版本列表** | 笔记与每日笔记都有「历史 · N」入口，列表含时间/来源/字数变化 |
| **版本快照与去重** | 内容无变化不写版本；改 AI 整理也算一次版本，标 `ai_organize` |
| **版本对比** | 行级 diff，绿加红删，顶部给出行数与标签变化摘要 |
| **版本恢复** | 二次确认，确认后当前内容先存版本再被替换；可再次恢复 |
| **容量保护** | 200 版 / 2 年 / 2 GB 天花板，只在保存时顺带检查，正常使用不触发 |
| **无收费痕迹** | 全部界面文案不含价格、套餐、升级、额度；版本数与恢复次数不受限 |

### P2 · 增强

剪藏（浏览器书签脚本 / URL 粘贴）、语音输入、提醒推送（依赖云函数定时触发，消耗平台侧云资源；**不向用户收费**）、答案沉淀、离线草稿、**「说说改了什么」AI 版本摘要**、待办状态变更历史。

### 依赖关系

```
P0 数据迁移 ──> P0 每日笔记/日历
          └──> P0 手动链接 ──> P1 AI 关联（复用同一张 links 表）
                          └──> P1 改名同步
P0 侧栏 ──> P1 集合（侧栏要展示"相关集合"）
P0 收件箱编辑 ──> P1 版本管理（要先有稳定的 update 路径，才能保证快照写对）
              └──> P1 改名同步（改名同步本身要写 link_sync 版本）
```

> 版本管理挂在 P1 开头而不是 P0，有个实际原因：P0 阶段编辑路径本身还在改（`[[ ]]` 解析、`daily_date` 回填），此时写快照容易漏写或写重。等 P0 的 update 路径稳定了再接快照，只需要改一处。

## 10. 明确不做

- 多人协作、分享链接、评论（个人工具，加了就是负担）
- 块级嵌套编辑器（与纯文本 + markdown 渲染的现有方案冲突）
- 数据库属性/视图/公式（Notion 那套过重）
- 端到端加密（与云端 AI 处理天然冲突）
- 独立移动 App
- 后台定时扫描全库建索引（成本高、当前体量收益低）
- 数据导出按钮（用户此前未采纳，本期不做；若后续要，单独评估）
- **版本的分支 / 合并 / 标签**（那是 Git，不是笔记；笔记只需要一条时间线）
- **版本回收站**（删掉的笔记连历史一起删，不做二次恢复）
- **版本快照的全文搜索**（搜历史会搜出一堆早已废弃的说法，反而干扰）
- **跨设备冲突合并**（后保存覆盖先保存，靠版本兜底，不做 CRDT）
- **任何形式的版本付费墙**（不收费、不订阅、不按次计费）
- **会员 / 专业版 / 企业版分层**（不做套餐，不做价格页，不做"升级"入口）
- **按版本数、笔记数、恢复次数设额度**（不存在额度这回事）

## 11. 风险与决策

| 风险 | 影响 | 应对 |
|---|---|---|
| 300 条加载上限 | 长期用户数据超出后，日历和侧栏算不全 | 本期加提示，P2 做分页 |
| `[[ ]]` 与用户正文冲突 | 用户本来就想打两个方括号 | 只在成对出现且内无换行时解析；提供"这段不解析"的转义 `\[[` |
| AI 关联噪音 | 推荐不准会让人不再看侧栏 | 阈值保守（≥8）、可否定、黑名单记忆 |
| 侧栏挤占内容宽度 | 1280px 以下体验下降 | 自动收起为竖线，记住用户选择 |
| 云函数提醒消耗平台资源 | 平台配额被提前用掉，可能影响其他功能 | P2 上线前说明清楚（不涉及用户付费），默认关闭 |
| **版本表体积增长快于预期** | 长文作者一天改十几次，单条笔记可能几百个版本 | 200 版 / 2 年 / 2 GB 三层天花板；不到 2 GB 不删任何东西 |
| **界面被误做成收费功能** | 一旦出现价格或"升级"字样，用户会以为要花钱 | 5.8.0 三条原则 + 5.8.5 禁止清单，作为验收硬项 |
| **快照写入失败导致丢内容** | 用户在"保存成功"的假象下失去旧内容 | 快照写在主体更新**之前**，快照失败则整体中止并报错，不静默继续 |
| **AI 整理静默覆盖手写内容** | 用户信任被破坏，这是最伤的一条 | AI 整理前强制留 `ai_organize` 快照；详情页对"最近被 AI 改过"的笔记显示提示条 |

### 已确认的决策（v1.2 定稿）

| # | 议题 | 结论 |
|---|---|---|
| 1 | 2.4 节纳入清单 | **全部同意**，按 P0/P1/P2 排期 |
| 2 | 「今天」与「每日笔记」 | 保持**两个页面**（偏看 / 偏记），导航分别是第一项和第三项 |
| 3 | `[[ ]]` 未命中 | **先提示再决定**（可新建，可忽略），不自动建空笔记 |
| 4 | AI 关联位置 | **只放详情页**，不进侧栏，保持侧栏降噪 |
| 5 | 版本管理 | **新增，纳入 P1**，见 5.8 / 6.1 / 9 节 |
| 6 | 版本管理收费 | **不收费**。不做价格、不做套餐、不做会员/专业版/企业版、不做席位与用量限制 |
